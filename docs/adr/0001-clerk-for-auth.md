# 1. Аутентификация через Clerk

**Статус:** Принято (задокументировано задним числом — решение и реализация
предшествуют этому ADR; см. PR #17 и цепочку фиксов #15–#21).

## Контекст

Расширению нужна аутентификация пользователя, чтобы:
- связать анонимные daily-лимиты с аккаунтом после входа;
- синхронизировать план (`free`/`pro`) между устройствами;
- получать стабильный `user_id` для Stripe (`stripe_customer_id`) и для
  подсчёта usage в D1.

Ограничение среды: код исполняется в Chrome-расширении (MV3 service worker +
side panel), а не на классическом сайте — часть auth-паттернов (redirect-based
OAuth, cookie-сессии) там работают иначе или не работают вовсе.

Первая попытка (см. `feature/auth-payments`, до появления PR-процесса) была
самописной: собственный auth endpoint на Worker'е, ручная выдача токена.
После итерации это было заменено на Clerk.

## Рассмотренные варианты

1. **Самописная аутентификация** (email+пароль или magic link, свой JWT).
   Полный контроль, ноль внешних зависимостей и стоимости.
   Минус: пароли, сброс, email-доставка, защита от брутфорса, revoke —
   весь этот периметр пришлось бы поддерживать самим на MVP-стадии проекта.
2. **Firebase Auth.** Зрелое решение, знакомый паттерн многим командам.
   Минус: слабее всего интегрируется именно с Chrome extension side panel
   flow (redirect-ориентирован), плюс отдельный вендор-лок в Google-инфру
   рядом с Cloudflare Workers.
3. **Clerk** (`@clerk/chrome-extension`) — выбрано.
   У Clerk есть выделенный SDK именно под Chrome-расширения, который решает
   проблему "как открыть окно логина из side panel/service worker" из коробки,
   плюс готовый JWT (RS256, JWKS), который бэкенд на Workers может проверять
   без SDK — просто `crypto.subtle.verify` (см. `backend/src/auth.ts`).

## Решение

Clerk как provider аутентификации на фронтенде (`@clerk/chrome-extension`),
верификация JWT на бэкенде через JWKS-эндпоинт Clerk без серверного Clerk SDK
(Cloudflare Workers V8 isolate — не Node, часть SDK там не запускается).

Для аналогии с Vue-миром: это похоже на связку Auth0/Vue или Supabase Auth —
внешний identity-provider, фронтенд получает JWT, бэкенд его просто проверяет
по публичному ключу, не общаясь с provider'ом на каждый запрос.

## Последствия

- Логин/логаут, сессии, refresh — не наша забота; экономит время на MVP.
- Зависимость от аптайма и pricing Clerk (сейчас — их бесплатный тир).
- Верификация JWT на бэкенде написана вручную (`verifyClerkJwt` в
  `backend/src/auth.ts`) — сознательно, чтобы не тащить Node-only Clerk
  backend SDK в Workers isolate; это означает ручную ответственность за
  корректность проверки подписи/exp/kid при апдейтах.
- Потребовалось несколько итераций после первого внедрения (#15–#21) —
  proxy для Clerk Frontend API через собственный домен, обработка
  анонимного flow, дублирующиеся toggle'ы в UI. Это уже отражено в истории
  PR, а не в этом ADR.
