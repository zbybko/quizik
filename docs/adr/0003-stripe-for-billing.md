# 3. Stripe для подписки Pro

**Статус:** Принято (задокументировано задним числом; см. PR #4, #10, #20,
#26 — checkout, customer portal, webhook, динамические redirect URL).

## Контекст

Нужен способ продавать подписку `free → pro` ($7/мес на момент написания,
см. `UsageCard.tsx`) из Chrome-расширения: чекаут, обработка успешной
оплаты, отмена подписки пользователем, синхронизация статуса `plan`
в D1 обратно на отмену/оплату.

Ключевое ограничение: платёжная форма не может открываться внутри
расширения (Chrome Web Store запрещает собирать данные карт напрямую в
расширении) — значит нужен внешний hosted checkout, на который расширение
только переходит по ссылке (`chrome.tabs.create`).

## Рассмотренные варианты

1. **Paddle** (Merchant of Record — сам считает и платит VAT/налоги).
   Плюс: меньше геморроя с международным налогообложением на старте.
   Минус: выше комиссия, менее гибкое API по сравнению со Stripe для
   кастомной логики (customer portal, webhook-события).
2. **LemonSqueezy** — похож на Paddle (тоже Merchant of Record), проще
   в интеграции для инди-проектов.
   Минус: моложе как продукт, меньше зрелость webhook/API по сравнению
   со Stripe на момент выбора.
3. **Stripe** (Checkout Sessions + Customer Portal + webhooks) — выбрано.
   Hosted Checkout закрывает ограничение "нельзя собирать карту внутри
   расширения" — просто редирект. Готовый Customer Portal избавляет от
   написания своего UI для отмены/смены способа оплаты. Webhook
   (`checkout.session.completed`, `customer.subscription.deleted`)
   синхронизирует `plan` в D1 без поллинга.

## Решение

Stripe Checkout Sessions для покупки, Stripe Customer Portal для управления
подпиской, вебхук на `/stripe/webhook` для синхронизации `users.plan` и
`stripe_customer_id` в D1 (см. `backend/src/stripe.ts`,
`backend/src/index.ts`).

Для аналогии с фронтенд-миром: это тот же паттерн, что Stripe Checkout в
любом Vue/Nuxt SaaS — фронтенд не трогает номера карт вообще, только
запрашивает `session.url` у бэкенда и делает редирект; вся чувствительная
часть (PCI DSS) остаётся на стороне Stripe.

## Последствия

- Redirect-based flow означает контекст переключается на новую вкладку
  (`chrome.tabs.create`), не modal внутри расширения — это осознанное
  ограничение Chrome Web Store policy, не недостаток самого Stripe.
- `payment/success` и `payment/cancel` — статические HTML-страницы на
  Worker'е (`backend/src/pages/payment.ts`), а не deep-link обратно в
  расширение — синхронизация статуса подписки идёт через `/user/status`
  при следующем открытии расширения, а не push-уведомлением.
- Success/cancel URL строятся динамически из `request.host` (PR #26), а не
  захардкожены — иначе dev/prod окружения ссылались бы на один и тот же URL.
- Webhook — единственная точка правды для смены `plan`; если вебхук не
  доставлен (Stripe retry исчерпан), статус в D1 разойдётся с реальным до
  ручного вмешательства. Мониторинга на этот случай пока нет — известный
  риск, не решение.
