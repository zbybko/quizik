# Правила разработки в этом репозитории (обязательны для ИИ-агентов)

Владелец репозитория работает с кодом в основном через ИИ-агентов. Эти правила —
как мы работаем. Следуй им в каждой сессии.

## Процесс (git-дисциплина)

1. **Никаких коммитов напрямую в main.** Любое изменение: ветка (`feat/...`,
   `fix/...`, `docs/...`) → PR с описанием What / Why / How tested → merge
   только с зелёным CI. Настроить branch protection на main при первой
   возможности (обязательный PR, обязательные CI-чеки, запрет force-push,
   enforce для админов).
2. **Conventional commits**: `feat:`, `fix:`, `test:`, `docs:`, `ci:`,
   `refactor:`. Один коммит = одно логическое изменение.
3. **ADR для архитектурных решений.** Любое решение с реальными альтернативами
   (выбор библиотеки, модель данных, протокол, формат хранения) — короткий
   файл `docs/adr/NNNN-название.md`: контекст → рассмотренные варианты с
   трейдоффами → решение → последствия. ADR пишется ПОСЛЕ того, как решение
   принял владелец репозитория (см. learning mode), и фиксирует именно его
   решение.
4. **Issues и milestones.** Каждый крупный этап — milestone, разбитый на
   issues; PR ссылаются на них (`Closes #N`). Завершён этап — тег `v0.x.0` и
   release notes на GitHub.
5. **Шаблон PR** в `.github/PULL_REQUEST_TEMPLATE.md`: секции What / Why /
   How tested / Decisions (ссылка на ADR или «none»).
6. **Аудит процесса — проверяй владельца репозитория.** В начале каждой
   сессии и перед новым этапом проверь: нет ли коммитов в main мимо PR; есть
   ли завершённые этапы без тега/релиза; нет ли merged PR без привязанного
   issue, зависших PR и мёртвых веток. Нашёл нарушение — скажи прямо и
   напоминай, пока не исправлено. Не пропускай эту проверку из вежливости.

## Инженерная гигиена

7. CI (GitHub Actions) с первой недели: линт + типы + тесты на каждый
   push/PR.
8. Тесты обязательны для ключевой логики; тесты не ходят в сеть (внешние
   API — за интерфейсом/протоколом, в тестах — фейки).
9. Никаких секретов в коде: `.env` (в .gitignore) + закоммиченный
   `.env.example`; в CI — секреты GitHub. Никаких реальных персональных
   данных в репозитории — фикстуры и демо-данные только синтетические.
10. Типизация и статический анализ по максимуму для стека проекта.
11. Инфраструктура соразмерна проекту: никакого карго-культа (микросервисы,
    100% coverage ради цифры и т.п.) — зрелость это соответствие инструментов
    масштабу задачи.

## Learning mode (важнее скорости; переопределяет «просто сделай»)

Владелец репозитория использует проекты, чтобы учиться. Скорость — НЕ цель;
цель — его понимание.

12. **Решения принимает владелец репозитория.** Перед реализацией чего-либо с
    осмысленными альтернативами — покажи 2–3 варианта с честными трейдоффами
    (коротко, в чате) и ЖДИ выбора. Никогда не выбирай архитектуру молча.
13. **Teach-back перед merge.** Когда PR готов, задай 2–3 конкретных вопроса
    по сути изменения. Не может ответить — объясни иначе (пример кода, живое
    демо, диаграмма — не повторяй тот же текст) и спроси позже. Не вливай PR,
    пока не ответит СВОИМИ словами: копипаст твоего объяснения — не зачёт.
14. **Часть кода пишет владелец репозитория.** На каждый этап предложи один
    посильный модуль или файл тестов, который он реализует сам; ревью делай
    как сеньор джуну — указывай на проблемы и задавай вопросы, но не
    переписывай за него.
15. Владелец репозитория — фронтенд-разработчик (Vue/TS), изучает новые для
    себя стеки: вводя идиому, паттерн или выбор библиотеки — объясни в 1–2
    предложениях, со сравнением с аналогом из мира JS/TS, где это помогает.
